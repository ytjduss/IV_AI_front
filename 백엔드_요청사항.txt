프론트 → 백엔드 API 요청 함수 정리
현재 프론트 코드 기준

1. 인증 / 회원정보
파일: src/api/auth.ts
서버: http://localhost:8000

signup(email, password)
- POST /auth/signup
- Header: Content-Type: application/json
- Body(JSON): { email, password }

login(email, password)
- POST /auth/login
- Header: Content-Type: application/json
- Body(JSON): { email, password }
- 응답에서 access_token을 사용

logout()
- POST /auth/logout
- Header: Authorization: Bearer <access_token>
- Body: 없음

getMyInfo(signal)
- GET /auth/me
- Header: Authorization: Bearer <access_token>
- Body: 없음
- 응답: { user_id, email, created_at }
- 참고: 현재 signal 인자는 fetch 옵션에 연결되어 있지 않음

2. 비전 / 자세 / 시선 분석
파일: src/app/lib/vision-api.ts
서버: http://localhost:8000
공통: session_id는 URL 쿼리 파라미터로 전달
현재 Authorization 헤더 없음

visionApi.calibrateFrame(sessionId, file)
- POST /vision/calibrate/frame?session_id={sessionId}
- Body(multipart/form-data): file (JPEG)

visionApi.finalizeCalibration(sessionId, signal?)
- POST /vision/calibrate/finalize?session_id={sessionId}
- Body: 없음
- 응답의 baseline을 반환

visionApi.gazeCheck(sessionId, file, signal?)
- POST /vision/gaze-check?session_id={sessionId}
- Body(multipart/form-data): file (JPEG)

visionApi.poseCheck(sessionId, file, signal?)
- POST /vision/check?session_id={sessionId}
- Body(multipart/form-data): file (JPEG)

visionApi.startAnswer(sessionId, signal?)
- POST /vision/answer/start?session_id={sessionId}
- Body: 없음

visionApi.summarizeAnswer(sessionId, signal?)
- POST /vision/answer/summary?session_id={sessionId}
- Body: 없음

visionApi.endSession(sessionId, signal?)
- POST /vision/end-session?session_id={sessionId}
- Body: 없음

3. 오디오 분석
파일: src/api/audio.ts
서버: VITE_AUDIO_API_BASE_URL (미설정 시 VITE_API_BASE_URL)
공통 Header:
- Accept: application/json
- ngrok-skip-browser-warning: true
- 현재 Authorization 헤더 없음

startAudioSession(sessionId)
- POST /audio/session-start
- Body(multipart/form-data):
  session_id: sessionId
  baseline_syllables_per_minute: "300"
  baseline_volume_db: "-20"

analyzeAudio(sessionId, file)
- POST /audio/analyze
- Body(multipart/form-data): session_id, file (녹음 파일)

getAnswerSummary(sessionId)
- GET /audio/answer-summary/{sessionId}
- Body: 없음

getSessionSummary(sessionId)
- GET /audio/session-summary/{sessionId}
- Body: 없음

endAudioSession(sessionId)
- POST /audio/end-session
- Body(multipart/form-data): session_id

참고
- 총 16개 API 요청 함수: 인증 4개, 비전 7개, 오디오 5개.
- signal은 요청 취소용 프론트 옵션이며 서버로 보내는 데이터가 아님.
- multipart/form-data의 Content-Type과 boundary는 브라우저가 자동 설정.
- 면접 시작 시 로그인 화면으로 이동시키는 조건문은 프론트 내부 처리이며 API 요청 함수가 아님.


============================================================
4. 미연결 API — 추가할 프론트 함수 및 호출 위치
============================================================
첨부 이미지에 있는 API 16개 기준입니다.
아래 함수명·파일 배치는 제안이며 아직 구현하지 않았습니다.
HTTP 메서드와 API 이름은 이미지 기준입니다.
이미지에 URL, 요청/응답 명세가 없으므로 경로와 정확한 필드명은 확정하지 않았습니다.
아래 인자는 프론트에서 필요한 정보의 개념이며 실제 전송 스키마가 아닙니다.
signal?은 공통으로 추가할 수 있는 요청 취소 옵션입니다.

------------------------------------------------------------
구현 시 공통으로 반영할 사항
------------------------------------------------------------
1) 위 16개는 미연결 함수의 설계안입니다. 기존 연결 함수 16개와 구분합니다.
2) 신규 API의 URL/Body/응답 타입은 백엔드 상세 명세를 받은 후 작성합니다.
3) 사용자 정보·이력서·면접·리포트 요청은 Bearer 인증 적용을 전제로 제안합니다.
   실제 인증 범위는 백엔드 명세로 확정하며, 공통 client.ts의 request에도
   인증 헤더 처리를 추가해야 합니다. 현재 공통 request에는 인증 처리가 없습니다.
4) 변경/저장 요청은 렌더 중 호출하지 않고 이벤트 핸들러에서 실행합니다.
   조회 요청은 화면 진입 효과로 실행하고 로딩/오류/취소 상태를 관리합니다.
5) 현재 실제 실행 경로는 App.tsx → InterviewScreen.tsx입니다.
   src/hooks/useInterviewSession.ts는 정의되어 있으나 src 내 사용처가 없습니다.

[17] 마이크 상태 확인
추가 함수 제안: checkMicrophone(file: Blob, signal?: AbortSignal)
추가 파일: src/api/audio.ts (기존 오디오 요청 함수와 함께 배치)
HTTP 메서드 / URL: 제공된 설명에 없으므로 확인 필요.
요청 형식 제안: multipart/form-data의 file에 1~2초 녹음 파일 전달.
- 정확한 파일 필드명, 지원 코덱/MIME, 인증 및 session_id 필요 여부는 확인 필요.
- 현재 다른 오디오 API의 session_id/baseline 값을 임의로 추가하지 않음.
- AUDIO_API_BASE_URL 사용 여부는 이 엔드포인트가 배포된 서버에 맞춰 확정.

성공 응답 타입:
type MicrophoneCheckResult = {
  avg_volume_db: number;
  status: "speech" | "noise" | "silent";
  is_noisy: boolean;
};

오류 reason 타입:
type MicrophoneCheckReason =
  | "no_file_uploaded"
  | "ffmpeg_extraction_failed"
  | "analysis_failed";

오류 안내 매핑:
- no_file_uploaded: 녹음 파일이 없습니다. 다시 테스트해 주세요.
- ffmpeg_extraction_failed: 오디오 파일을 처리하지 못했습니다.
- analysis_failed: 마이크 음성 분석에 실패했습니다. 다시 시도해 주세요.
오류 응답의 전체 구조와 HTTP 상태 코드는 별도 확인 필요.
현재 공통 request는 HTTP 오류 또는 success === false를 실패로 처리하므로,
서버가 200 + reason만 반환한다면 checkMicrophone에서도 오류 판별 필요.

호출 위치: src/screens/DeviceTestScreen.tsx
- getUserMedia 성공 후 audioTrack 확보 지점에서 테스트 녹음 시작.
- 영상이 포함되지 않은 오디오 전용 MediaStream으로 MediaRecorder 구성.
- 1~2초 녹음 파일을 완성한 뒤 checkMicrophone으로 전달.
- 한 요청이 끝난 후 다음 녹음/전송을 진행해 요청 중첩과 대기열 누적 방지.
- 서버가 각각의 파일을 FFmpeg로 읽으므로 청크마다 독립 디코딩 가능해야 함.
  MediaRecorder.start(timeslice)의 후속 청크가 독립 파일이라고 가정하지 말고,
  녹음 시작/정지 단위로 파일을 완성하거나 서버의 연속 청크 지원 여부 확인.

현재 함수/상태에 맞춘 변경 지점:
1) measureAudio() / micLevel
   - 기존 Web Audio API 측정과 볼륨 바는 그대로 유지.
   - API avg_volume_db를 볼륨 바의 값으로 사용하지 않음.
   - 브라우저의 기존 dBFS 값과 서버의 avg_volume_db를 같은 척도로 비교하지 않음.

2) micOk
   - 현재 audioTrack의 live/enabled 상태를 나타내는 장치 연결 값으로 유지.
   - silent라고 해서 마이크 연결 실패로 바꾸지 않음.

3) 신규 micStatus / micCheckError / micChecking
   - micStatus: "waiting" | "speech" | "noise" | "silent"
   - speech: 음성이 감지되고 있습니다.
   - noise: 주변 소음이 감지됩니다.
   - silent: 마이크에 대고 말씀해 주세요.
   - API 오류는 silent/noise와 구분하여 표시하고 재시도 제공.

4) noiseOk / ambientLevel
   - 현재 3초간 ambientSamples 평균 < 35로 판단하는 로컬 소음 판정을
     서버 응답의 is_noisy 기준으로 교체.
   - 성공 응답에서 noiseOk = !is_noisy.
   - 로딩/오류 때는 미확인 상태를 따로 표시하고 이전 성공값을 확정값처럼 표시하지 않음.
   - ambientLevel은 현재 로컬 0~100 값이므로 서버 dB를 그대로 대입하지 않음.
     숫자가 필요하면 avgVolumeDb 상태를 별도로 두고 dB 단위로 표시.

5) 정리 및 면접 시작

백엔드 판정 규칙 (전달받은 명세)
- FFmpeg로 WAV 변환 후 Praat(parselmouth)로 평균 음량/유성음 비율 계산.
- avg_volume_db < 40: silent
- 위 조건이 아니고 voiced_ratio >= 0.15: speech
- 그 외: noise
- is_noisy는 status == "noise"일 때 true.
- voiced_ratio는 내부 판정값이며 제공된 응답 필드에는 포함되지 않음.
- 프론트는 규칙을 재계산하지 않고 서버가 반환한 status/is_noisy 사용.
